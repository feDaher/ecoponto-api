# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product context

This repo (`ecoponto-api`) is the **backend** for **EcoPonto Digital**, a system (academic project, UniFacig ADS course) for mapping and credentialing recyclable/e-waste collection points in Manhuaçu–MG. Full product scope per the project's C4 architecture documentation (`ECOPONTO_Documentacao_de_Software_Modelo_C4.pdf`, supplied by the professor/orientador — summarized here so it doesn't need to be re-read):

- **Three actor profiles** (matches `Role` enum: `CITIZEN`/`COLLECTOR`/`ADMIN`):
  - **Cidadão** (`CITIZEN`): browses the map (public, no login required), filters by waste type/proximity/city, traces routes, requests collection, accumulates gamification points, rates collection points.
  - **Coletor/Cooperativa** (`COLLECTOR`): registers and manages their own collection point(s), updates hours, receives requests, logs received materials, exposes a WhatsApp contact button.
  - **Administrador** (`ADMIN`): approves/moderates collection points before they appear on the map, moderates reviews/content, manages users, publishes educational content.
- **MVP functional scope**: georeferenced map of collection points, filters, detailed point info, route tracing, user registration/login, point credentialing+approval workflow, WhatsApp contact channel, environmental education content module, gamification (points/ranking/badges for disposals), point reviews/ratings, Google Maps integration.
- This backend currently implements: health-check, auth/RBAC (register, login, me, per-role `/admin` `/collector` `/citizen`), the Google Places proxy (`src/modules/places/`), collection points with admin approval and public search by city/waste type/radius (`collection-points/`), waste categories CRUD (`waste-categories/`), operating hours CRUD plus the daily outdated-hours job (`operating-hours/`), public educational content per category (`educational-content/`), review listing + admin moderation (`reviews/`, BE-09), reports/export (`reports/`, BE-08) the disposal log / recycling history (`disposals/`, FE-16) and the user's own account (`PATCH`/`DELETE /users/me`). Gamification (ranking, badges) is **not yet built**, nor are review creation (`POST /collection-points/:id/reviews`), notifications or WhatsApp.

### Business rules to honor when building those modules

- Registration (name, email, phone, city) is required only for _active_ interactions (requesting collection, logging a disposal, gamification). **Public map browsing and educational content must never require login.**
- A collection point is invisible on the map until an `ADMIN` approves it (checks address, accepted waste types, hours, contact info).
- A collection point must have valid GPS coordinates or a verifiable full address — reject registration without one.
- A collection point must declare its accepted waste categories from a standard taxonomy (min. set: plastic, paper, metals, glass, used cooking oil, general electronics, batteries, cell phones, computers, printers, televisions). No categories → cannot be approved.
- A collection point must declare operating hours at registration; if not updated in 60+ days, auto-flag it on the map as "possibly outdated."
- Search/filter combines waste type + proximity radius (km) + city, plus route tracing to the selected point, plus a deep link that opens the route directly in Google Maps.
- WhatsApp contact button on a point's detail page only if the collector opted in to show their number.
- Disposal logging converts to gamification points (rules consider waste type, quantity, frequency) feeding a ranking/badges/seals system.
- Educational content is per waste category, public, no login needed.
- Authenticated users can rate/comment on collection points; admin can moderate reviews.
- Non-functional targets called out in the docs: search/filter responses <2s, LGPD-compliant data handling (explicit consent, anonymization where possible, right to erasure, access-restricted + audited logs).

## Current implementation (this repo)

Express 5 + TypeScript API, organized as **Clean Architecture applied per feature module**, not as global top-level layers. Each business feature under `src/modules/<name>/` has its own:

- `domain/` — entities, repository interfaces, use-cases (framework-agnostic business logic)
- `infra/` — concrete implementations (Prisma repositories, external HTTP clients)
- `presentation/` — Express routes/controllers, Zod validators

`src/modules/auth/` is the reference implementation of this pattern — follow its shape (`domain/{entities,repositories,use-cases}`, `infra/{repositories,http}`, `presentation/{*.controller,*.routes,*.validators}`) when adding new modules. `src/modules/health/` and `src/modules/users/` are intentionally thin (no domain/infra layers) since they don't have real business logic yet. `collection-points/`, `waste-categories/`, `operating-hours/` and `educational-content/` follow the layered shape. In `collection-points/` the routes only wire middlewares to `collection-points.controller.ts`, which calls one domain use-case per operation; persistence lives in `PrismaCollectionPointRepository` (CRUD/moderation) and `PrismaCollectionPointSearchRepository` (public search), and the presentation layer never imports Prisma. `waste-categories/` is the single module for the category taxonomy — reuse its repository instead of creating another one.

### Collection point search (BE-07)

`GET /collection-points` is public and combines optional filters: `city` (exact, case/accent-insensitive through the column collation), `wasteType` (one or more comma-separated category codes, matched with OR through an `id IN (SELECT ... FROM PointCategory JOIN WasteCategory ...)` subquery with a `SEMIJOIN(MATERIALIZATION)` hint over active, accepting categories; `SearchCollectionPointsUseCase` checks the codes against the catalog in parallel with the search and answers 400 for unknown or inactive ones), and `latitude` + `longitude` (+ `radius` in km, max 100). Everything is validated by `searchCollectionPointsQuerySchema` (blank params are ignored, repeated or malformed ones are 400, latitude/longitude must come together and `radius` needs both). `limit` defaults to 100 (max 500); `X-Total-Count` (exposed through CORS) carries the number of matches before `limit`. With a reference point, items carry `distanceKm` and are ordered by distance; otherwise by name. Only `APPROVED` points are ever read. Public point responses list only categories with `PointCategory.isAccepting = true`.

Performance rules worth keeping (measured with `load-test`, 5000 points, 100 connections, p99 < 2 s in every scenario):

- Ranking and the radius cut run in SQL (`PrismaCollectionPointSearchRepository`, Haversine in `$queryRaw` plus an index-friendly bounding box), so only `limit` rows are hydrated by a second `findMany({ id: { in } })`. Fetching every candidate and filtering in Node was 5-10x slower and timed out under load.
- `COUNT(*)` only runs when the page comes back full.
- Indexes `(status, name)`, `(status, city, name)` and `(status, latitude, longitude)` serve the ordering and range predicates; `(status, city)` was dropped as a redundant prefix.
- Cost is proportional to the response size: throughput was ~110 req/s at `limit=200`, ~190 at 100 and ~290 at 50, hence the default of 100. Use `prisma` (primary), not `prismaRead`: this is not a report query.
- The Haversine expression in SQL and `distanceInKm` (`src/shared/geo/distance.ts`) must stay equivalent; `boundingBox` must always be a superset of the circle.

### Disposals / recycling history (FE-16)

A citizen logs a disposal with `POST /disposals` (`collectionPointId`, `categoryId`, `weightKg` ≤ 1000, optional `disposedAt` between 30 days ago and now; the citizen is always the token's user). The point must be `APPROVED` (else 404), the category active (else 404) and accepted by the point through `PointCategory` (else 422). It starts `PENDING` with 0 points; **points are credited only when the point's collector (or an ADMIN) confirms** via `PATCH /disposals/:id/status` (`CONFIRMED` → `calculatePoints`, 10/kg, min 1; or `CANCELLED` → 0). The transition is an `updateMany ... where status = PENDING`, so concurrent confirmations cannot score twice (409). `GET /disposals/me` (+ `/summary`, CONFIRMED only) is the citizen's own history; `GET /disposals/received` is the collector's points; `GET /disposals/:id` answers 404 (not 403) to anyone who is not the citizen, the point's collector or an ADMIN. Collector/admin views expose only the citizen's id and name. BE-08 reports already count only `CONFIRMED` disposals by default. The points rule is a placeholder until the gamification module exists.

### Collection-point material settings (BE-19)

`PointCategory.capacityKg` is an optional storage limit (`Decimal(10,3)`); `null` means no limit. `PointCategory.isAccepting` defaults to `true`, so existing links continue receiving after migration. `PATCH /collection-points/:id/materials/:categoryId` updates either field (or both); only the point owner or an ADMIN may call it, and the category must already be linked to the point. A paused category remains in the point's portfolio, is omitted from public `wasteCategories` and `wasteType` search results, and causes `POST /disposals` to answer 422 until reception is reactivated.

### Ranking (RB09)

`src/modules/ranking/` turns CONFIRMED disposals into the gamification ranking (same rule as `/disposals/me/summary`, so a citizen's score matches their own history). `GET /ranking` is public (`city`, `limit` 20, max 100) and returns only `{ position, name, city, points }` with the **first name** — no user ids, the same LGPD minimization as public reviews. Positions use competition ranking (ties share the position: 1, 1, 3). `GET /ranking/me` (CITIZEN) returns the caller's own `{ position, name, city, points }`, `position: null` while they have no confirmed points or are outside the filtered `city`; the apps use it to highlight the user instead of the public list exposing ids. Aggregation runs with Prisma `groupBy` over `DisposalRecord` (active citizens only).

### Reviews and moderation (BE-09)

`GET /collection-points/:id/reviews` is public: only reviews with `isHidden = false` of an `APPROVED` point (otherwise 404), newest first, `limit` (20, max 100) + `offset`, total in `X-Total-Count`. Items carry only `authorName` = the citizen's **first name** (LGPD minimization: no citizen id or full name in public). `POST /collection-points/:id/reviews` (CITIZEN, body `{ rating 1–5, comment? ≤ 500 }`, blank comment → null) publishes a review of an `APPROVED` point (otherwise 404); the author is always the token's user. One review per citizen per point: posting again updates the rating/comment of the previous one (200) instead of creating another (201), so the average cannot be inflated, and an edit never changes `isHidden`. Moderation is ADMIN-only: `GET /admin/reviews` (`visibility=visible|hidden|all`, `collectionPointId`, same pagination; includes author id/name and point), `PATCH /admin/reviews/:id/hide` and `/unhide` (reversible, idempotent; hiding is the default moderation action) and `DELETE /admin/reviews/:id` (permanent, for content that must not be kept). Writes go through `auditTrail` as `RESOURCE_CHANGED` with the review id.

### Collection point categories and hours

Collection point categories are normalized through `PointCategory`, linked to active `WasteCategory` records by their `name` code. The `POST`/`PUT /collection-points` API accepts and returns `wasteCategories` as a list of codes for frontend compatibility; handlers translate that API field to relation writes, and public search filters through the relation. The BE-16 migration backfills existing JSON values before dropping the old column. Operating hours live only in the `OperatingHours` table (BE-17): `POST /collection-points` requires `operatingHours` (each with `openTime` < `closeTime`) and writes them in the same nested create as the point; `PUT` rejects `operatingHours` with 400 (hours change only through `/collection-points/:id/operating-hours`); every point response carries the active rows as `hours` (`HH:mm`), including the public search. The BE-17 migration copies the old JSON into the table, skipping only slots that already exist there, before dropping the column.

### Collection point location (BE-04, RN04)

`POST`/`PUT /collection-points` never trust the client location as-is: the handler passes `latitude`/`longitude`/`placeId` through `ResolveLocationUseCase` (`src/modules/geolocation/`) before writing. Accepted inputs: GPS coordinates (both fields, inside the Brazil bounding box in `location-rules.ts` — this rejects `0,0`, swapped lat/long and other countries), a `placeId` from `GET /places/autocomplete` (the server calls Google itself and uses the confirmed coordinates), or both (then the pin must be within `MAX_DISTANCE_FROM_ADDRESS_KM` = 1 km of the verified address). Missing/semantically invalid location → **422**; malformed body (e.g. latitude as a string, `placeId` outside `[A-Za-z0-9_-]{1,512}`) → 400 from Zod. Ownership is checked before any Google call on `PUT`. Address verification fails closed: Google unavailable or no `GOOGLE_MAPS_API_KEY` → 503 and nothing is stored (students without a key can still register with coordinates). `CollectionPoint.locationSource` (`GPS_COORDINATES` | `VERIFIED_ADDRESS`) and `placeId` record how each location was established, for the admin approval step. The bounding box approximates Brazil (it also covers e.g. parts of Paraguay); real address verification comes from the `placeId` path. Governance caveat: Google's terms allow storing `placeId` indefinitely but Places-derived lat/long only for 30 days — before any production use, refresh coordinates from the stored `placeId`. Distance math lives in `src/shared/geo/distance.ts` (`distanceInKm` for the address check, `boundingBox` for the search).

### Outdated hours flag (BE-05)

`CollectionPoint.hoursConfirmedAt` is reset to now (and `isOutdated` to false) whenever the collector creates/updates/deletes operating hours (and on point creation). Resubmitting the point via `PUT /collection-points/:id` does **not** touch it, since that route no longer changes hours. `startOutdatedHoursJob()` (`node-cron`, started from `server.ts`, daily 03:00 America/Sao_Paulo) flags points with `hoursConfirmedAt` older than 60 days as `isOutdated = true`; the flag is returned by the public collection-point endpoints. Only the point owner or an ADMIN may change a point's hours (`ensureCanManageCollectionPoint`).

### Request pipeline (`src/app.ts`)

Middleware order matters: `helmet` → `cors` → `express-rate-limit` (`RATE_LIMIT_MAX` req/15min per IP, default 100) → `express.json()` → `auditTrail` → `/docs` (Swagger UI) → feature routes → `notFound` → `errorHandler` (must stay last).

Deploy hardening (all opt-in or invisible to the apps):

- `TRUST_PROXY` (env) feeds `app.set("trust proxy")`. Unset → off (local). Behind a reverse proxy it **must** be set (hop count, usually `1`, or proxy IPs/subnets), otherwise every limiter sees the proxy's IP and throttles all users together. `"true"` is rejected at boot (clients could spoof `X-Forwarded-For`).
- `CORS_ORIGINS` (env, comma separated) restricts browser origins; unset → `*` (fine with Bearer auth, no cookies). Native mobile apps are unaffected by CORS.
- `errorHandler` turns body-parser errors (`expose: true`, 4xx) into their status with a fixed message: malformed JSON → 400, body > 100 KB → 413. Everything else that isn't an `AppError` stays a generic 500.
- `GET /health` is liveness (no DB). `GET /health/ready` runs `SELECT 1` (3 s timeout) → 200 or 503; use it for the platform's readiness/health probe. Both are skipped by the global rate limiter.
- `server.ts` handles `SIGTERM`/`SIGINT` via `createShutdownHandler` (`src/shared/lifecycle/graceful-shutdown.ts`): stop the cron job, `server.close()` (in-flight requests finish), `$disconnect` the Prisma clients, exit; forced exit 1 after 10 s.

Route handlers are plain async functions — **do not wrap them in a try/catch-to-next helper**. Express 5's router natively forwards rejected promises to the error middleware (verified in `node_modules/router/lib/layer.js`), so throwing an `AppError` (`src/shared/errors/AppError.ts`) from anywhere in a request, sync or async, reaches `errorHandler` automatically.

### Auth & RBAC

Firebase is the identity provider; there is no separately-issued JWT — **the Firebase ID Token itself is the bearer token** used on protected routes (this matches the project docs, which also specify Firebase Auth + JWT-based sessions).

- **Register** (`POST /auth/register`): backend creates the Firebase user via Admin SDK (`RegisterUserUseCase`), then mirrors it into the local `User` table (`PrismaUserRepository`) keyed by `firebaseUid`. Required fields are `name`, `email`, `password`, `phone`, `city` — matches the docs' "Cadastro obrigatório" rule (name/email/phone/city). Self-registration is restricted to `CITIZEN`/`COLLECTOR` (see `auth.validators.ts`) — there is no endpoint to self-register as `ADMIN`; promote a user by updating `role` directly in the database.
- **Login** (`POST /auth/login`): the Admin SDK cannot verify passwords, so `LoginUserUseCase` calls the Firebase Identity Toolkit REST API directly (`FirebaseAuthRestClient`, needs `FIREBASE_API_KEY`, the Web API key — different from the Admin SDK service-account credentials) to exchange email/password for an ID token. (Docs also mention social login via Google/Facebook — not implemented yet.)
- **Login errors and throttling**: `FirebaseAuthRestClient` never forwards Firebase error codes. Wrong email/password codes (`INVALID_LOGIN_CREDENTIALS`, `EMAIL_NOT_FOUND`, `INVALID_PASSWORD`, `INVALID_EMAIL`, `USER_DISABLED`) all become 401 `Invalid credentials` (no account enumeration), Firebase lockout `TOO_MANY_ATTEMPTS_*` → 429, any other Firebase error → 502, network/timeout (5s) → 503. Logs carry only the Firebase status/code. `POST /auth/login` (20) and `POST /auth/register` (10) have per-IP limiters per 15 min on top of the global one. Validators trim text fields, lowercase the email and cap lengths at 191 (Prisma `String` = `VARCHAR(191)`), phone 20, password 128.
- **Session refresh** (`POST /auth/refresh`, body `{ refreshToken }`): ID tokens last one hour, so the apps exchange the `refreshToken` returned by login for a new `{ idToken, refreshToken, expiresIn }`. `RefreshSessionUseCase` calls Firebase's Secure Token API through `FirebaseAuthRestClient.refreshIdToken` (the Web API key stays on the server) and applies the same checks as login: no local `User` row → 401, blocked → 403. Expired/revoked refresh tokens → 401 "Session expired, log in again" (the client must log in again). Per-IP limiter of 60 per 15 min — higher than login, since every signed-in app renews hourly and a classroom shares one IP.
- **Protected routes**: `authenticate` middleware (`src/middlewares/authenticate.middleware.ts`) verifies the `Authorization: Bearer <idToken>` header via `firebaseAuth.verifyIdToken`, then loads the local `User` row by `firebaseUid` and attaches it to `req.user` (`id`, `firebaseUid`, `email`, `role` for the guards, plus the profile `name`, `phone`, `city`, `createdAt`, so `GET /auth/me` returns the whole profile without a second query). A valid Firebase token for a user with no local `User` row is rejected (401) — Firebase and the local DB must stay in sync through `/auth/register`.
- **authenticate** verifies the token with `verifyIdToken(token, true)` (revoked tokens and disabled accounts are rejected) and accepts the `Bearer` scheme case-insensitively. Only Firebase `auth/*` errors become 401; anything else (network, DB) propagates as 500 so outages are not disguised as "invalid token". It also snapshots `req.params` into `res.locals.requestParams` for the audit trail.
- **RBAC**: `authorize(...roles)` (`src/middlewares/authorize.middleware.ts`) checks `req.user.role` against an allow-list, e.g. `authorize(Role.ADMIN)` on `GET /users`. It throws at boot if called with no roles, and exposes its frozen role list under the `AUTHORIZED_ROLES` symbol so tests can inspect it. Route order is enforced by tests: `authenticate` first, `authorize` second, then `validate`/handler — never validate before authorizing.
- **ABAC (ownership)**: attribute rules live in `src/shared/security/access-policy.ts` (`isOwner`, `isOwnerOrAdmin`, `assertOwner`, `assertOwnerOrAdmin` → 403). `PUT /collection-points/:id` is owner-only; operating hours are owner-or-admin (`ensureCanManageCollectionPoint`). Reuse these helpers instead of inline `if (x.ownerId !== req.user.id)` checks.
- **Access matrix (governance)**: `tests/security/access-matrix.ts` is the reviewed source of truth for who may call every route (`PUBLIC`, `ANY_AUTHENTICATED` or a role list). `route-policy.spec.ts` introspects the real Express router and fails if a route is missing from the matrix, a matrix entry is stale, the roles in code differ, the guard order is wrong, or a write route is public outside `PUBLIC_WRITE_ALLOWLIST`. `rbac-matrix.spec.ts` then hits every protected route over HTTP with no token, malformed/forged/revoked tokens, an unregistered user and each of the 3 roles. **Adding or changing a route means updating the matrix** — that diff is what reviewers check.
- **Audit trail**: `auditTrail` (global, right after `express.json()`) writes an `AuditLog` row on `res.finish` for every 403 by an authenticated user (`ACCESS_DENIED`) and every successful POST/PUT/PATCH/DELETE by one (`RESOURCE_CHANGED`), with userId, method, route **pattern** (never the raw URL), resource id param and status. Bodies, headers and tokens are never stored. Recording is fire-and-forget: a failing audit store logs `[audit-trail] failed to record entry` but never breaks the response. `AuditLog.userId` is nullable with `onDelete: SetNull`, so deleting a user (LGPD erasure) anonymizes their log rows instead of being blocked. Reads are not audited unless the route opts in with `auditRead(action)` (placed after `authorize`); it records only on 2xx.
- **Audit trail listing (BE-18)**: `GET /admin/audit-logs` (ADMIN only, itself recorded as `AUDIT_LOG_VIEWED` through `auditRead`) pages newest-first by `(createdAt, id)` with an opaque base64url cursor (`domain/rules/audit-log-cursor.ts`), `limit` 20 (max 100), response `{ items, nextCursor }`. Optional filters `action`, `userId`, `route`, and `from`+`to` (sent together, max 90 days). Read-only: there is no route to edit or delete a log row.
- `req.user` typing is added via module augmentation in `src/types/express/index.d.ts`.
- **Firebase ↔ DB consistency on register**: `RegisterUserUseCase` creates the Firebase user first; if the local `User` insert then fails, it deletes the Firebase user (compensation) before rethrowing. Without that, the email would be stuck as "already registered" (409) while having no local row (401 on every protected route). Keep this compensation pattern in any future flow that writes to both Firebase and the DB.

### My account (`/users/me`)

Self-service routes for the logged-in user. The target is **always** the token's user (no id in the URL); the matrix lists the three roles explicitly, so the guard chain is `authenticate` → `authorize(CITIZEN, COLLECTOR, ADMIN)` → `auditSelf` → `validate`. `auditSelf` (in `audit-trail.middleware.ts`) makes the audit row carry the user's own id as `resourceId`, since there is no `:id` param. A blocked account gets 403 from `authenticate` before reaching either route.

- `PATCH /users/me` (`UpdateOwnProfileUseCase` → `IUserRepository.updateProfile`): `z.strictObject` with `name`, `phone` and `city`, all required. `name` and `city` are trimmed with inner spaces collapsed, letters/spaces/`'.-` only, max 191; `name` needs at least two words (first and last name), `city` at least 2 characters. `phone` accepts a mask (digits, spaces, `().-`) and is stored as digits only, 10 or 11 digits (DDD + number). Any other field (`email`, `role`, `isBlocked`…) → 400: the email is the Firebase login and does not change here. 200 returns the full `User` row, the same shape as `user` in `POST /auth/login`. Validation and domain messages are in Portuguese because the web app shows them as they come.
- `DELETE /users/me` (`DeleteOwnAccountUseCase`, LGPD right to erasure) **anonymizes instead of deleting the row**: `CollectionPoint.collector`, `Collection.collector`, `DisposalRecord.citizen` and `Review.citizen` have no `onDelete` (Restrict), and disposals, reviews, reports and MTRs must stay consistent. In one transaction (`IUserRepository.anonymize`): the row becomes `name = "Usuário removido"`, `email = removido-<id>@anonimo.ecoponto.invalid` (unique, `.invalid` is a reserved TLD), `phone = ""`, `city = ""`, `isBlocked = true` (`firebaseUid` is kept, it is an opaque id); then, **before the commit**, the Firebase account is deleted (`IFirebaseUserManager.deleteUser`; `auth/user-not-found` counts as done). If Firebase fails the transaction rolls back and the API answers 502, so the database never ends up anonymized with the login still alive. The opposite window (Firebase deleted, commit fails) is only logged (`[users/me] Firebase account deleted but anonymization did not commit`): the login is gone either way, and the user can no longer authenticate to retry, so an admin must finish it. The old token then fails: `verifyIdToken(token, true)` rejects a deleted user (401), and even a token Firebase still accepted hits the blocked row (403). 204 with no body.
- **Last admin**: an `ADMIN` cannot delete their own account when no other active (not blocked) `ADMIN` exists → 409. The check runs inside the same transaction with `SELECT ... FOR UPDATE` on the active admins, so two admins deleting themselves at the same time cannot leave the system without one.
- **Pending (collectors)**: an anonymized collector's collection points stay linked to the anonymized user and keep their status. An admin may need to reassign or deactivate them; there is no route for that yet.
- Out of scope for now: password change, nickname and notification preferences (they need new columns).

### Shared Firebase project & seed

This is a class project: the professor (orientador) owns a single **dev** Firebase project, and every student gets its credentials (`FIREBASE_*` in `.env`) through a private channel — students do not create their own Firebase project. Each student runs their **own** local MySQL (Docker). Consequences:

- Firebase Auth users are shared across the whole class; `User` rows are per-machine. A user registered on one student's machine exists in Firebase but not in another student's DB: re-registering that email → 409, logging in works but protected routes → 401. This is expected, not a bug.
- `npm run db:seed` (`src/database/seed.ts`) seeds `admin@ecoponto.dev` (ADMIN), `coletor@ecoponto.dev` (COLLECTOR), `cidadao@ecoponto.dev` (CITIZEN), all with password `Ecoponto@123`. It is **find-or-create** in Firebase: it only sets the password when creating the account, and never updates existing Firebase accounts — so one student running it can't change the shared accounts for everyone. It first upserts the 11 standard waste categories in one transaction (`PLASTIC`, `PAPER`, … — same codes accepted by the collection-point API; done before the users so a Firebase failure still leaves the taxonomy in place), then upserts the local `User` row by email (refreshing `firebaseUid`). Idempotent; refuses to run with `NODE_ENV=production`.
- The seed is the only way to get an `ADMIN` in a fresh environment (no admin self-registration).
- After the accounts, `seedDemoData` (`src/database/seed-demo.ts`) adds the demo data the apps need to show something: 8 collection points in Manhuaçu owned by `coletor@ecoponto.dev` (7 `APPROVED`, one with hours confirmed 95 days ago → RB06; one `PENDING` → RB03), 5 published educational guides (Markdown `content` with the headings `## Como descartar`, `## Por que reciclar`, `## Impacto ambiental`, which the mobile app splits into sections), 3 reviews and 4 `CONFIRMED` disposals of `cidadao@ecoponto.dev` (so the ranking is not empty). Rows have fixed UUIDs and are only created when missing — re-running never overwrites edits. It mirrors the mobile app's offline demo, so the map looks the same with or without the API.
- Never commit credentials, and a production deployment must use a separate Firebase project.

### Prisma client generation

`prisma/schema.prisma` uses the newer `prisma-client` generator (TypeScript source, not the classic `@prisma/client` codegen), with `output = "../src/generated/prisma"`. It **must** be generated inside `src/`, not at the project root — `tsconfig.json` has `rootDir: "src"` + `include: ["src/**/*"]`, and since the generated files are plain `.ts` that gets compiled with the rest of the app (imported via relative paths, e.g. `src/config/prisma.ts`), anything outside `src` would fail with TS6059 (`rootDir` violation). `src/generated/` is gitignored (matched by the `generated/` rule) and regenerated via `npx prisma generate`.

The Prisma client is instantiated with the `@prisma/adapter-mariadb` driver adapter, not the classic connection-string-in-schema approach — see `src/config/prisma.ts`. The adapter always creates a `mariadb` connection pool; `prisma.ts` passes it the `DATABASE_URL` string with pool options (`connectionLimit`, `acquireTimeout`, `idleTimeout`, `connectTimeout`) appended as query params from `DB_POOL_*`/`DB_CONNECT_TIMEOUT_MS` env vars, only when the URL doesn't already set them (URL wins). Keep passing the URL string rather than a parsed host/user/password object, so other driver options in the URL query aren't silently dropped. Default pool size 20 was chosen from load tests (throughput plateaus above ~20 connections; see README). That adapter wraps the `mariadb` npm package (MariaDB Corp.'s connector), which despite the name talks to plain MySQL servers fine over the MySQL wire protocol — including MySQL 8's default `caching_sha2_password` auth plugin, but the first login after a server start without TLS needs the server's RSA key, so `prisma.ts` adds `allowPublicKeyRetrieval=true` outside production (verified in `node_modules/mariadb/lib/cmd/handshake/auth/caching-sha2-password-auth.js`; production must use TLS instead). The URL-building logic lives in `src/config/database-url.ts` (`buildConnectionUrl`) and is shared by both clients below.

**Primary/replica split (BD-06)**: `prisma.ts` exports two clients. `prisma` → primary (`DATABASE_URL`), for every write and all normal reads. `prismaRead` → read-only replica (`DATABASE_REPLICA_URL`, falls back to `prisma` when empty), typed as `ReadOnlyPrismaClient` (only `find*`/`count`/`aggregate`/`groupBy`/`$queryRaw` compile). Use `prismaRead` **only** for heavy report/dashboard queries that tolerate replication lag — never for read-after-write. Each client has its own pool with the same `DB_POOL_*` limits. Writes are blocked three ways: the type, the replica user `ecoponto_reader` (SELECT only), and `super_read_only` on the replica. `tests/support/prisma-mock.ts` exports `prismaRead = prisma`.

### Local database (`docker-compose.yml`)

`npm run db:up` (`docker compose up -d --wait`) starts two MySQL containers: the primary `mysql` (port `${MYSQL_PORT:-3306}`, database/user/password baked into its `environment` block, matching `DATABASE_URL` in `.env.example`, data in the `ecoponto_mysql_data` volume) and the GTID replica `mysql-replica` (port `${MYSQL_REPLICA_PORT:-3308}`, volume `ecoponto_mysql_replica_data`). The `--wait` flag blocks until both healthchecks pass: the primary's `mysqladmin ping` over TCP (`-h 127.0.0.1`, so the init-time temp server doesn't count) and the replica's check that both replication threads (IO and SQL) are running — so there's no race with `prisma migrate dev`, and broken replication fails `db:up` loudly. Init scripts run only on a fresh volume: `docker/mysql/init/` creates the `replicator` and `ecoponto_reader` users on the primary (replicated to the replica), and `docker/mysql-replica/init/` points the replica at the primary and sets `super_read_only`. The replica has no `MYSQL_DATABASE`/`MYSQL_USER` on purpose: they arrive through replication, and creating them locally would conflict with the replicated `CREATE USER`. Migrations run only against the primary. Volumes created before BD-06 lack those users and the GTID history → `npm run db:reset`. `npm run db:replica:status` shows `SHOW REPLICA STATUS`. `npm run db:reset` drops the volume (all data) and recreates it — destructive, dev-only.

### Config (`src/config/`)

`env.ts` validates `process.env` with Zod at import time and throws immediately if anything is missing/invalid — this is the first thing that runs (imported transitively by nearly everything), so a missing env var fails fast at boot rather than surfacing as a runtime error deep in a request. `firebase.ts` and `prisma.ts` both depend on `env` being valid. `swagger.ts` builds the OpenAPI spec from JSDoc `@openapi` comments in `src/modules/**/presentation/*.routes.ts` (glob path is relative to `process.cwd()`, i.e. only works when run from the project root — this only picks up routes documented with `@openapi` blocks, and only from `.ts` source, so it will not find routes after a production `dist/` build; acceptable for now since Swagger is a dev-time contract tool).

### Places / Google Maps (`src/modules/places/`)

Public proxy to **Places API (New)** for the address search box of the web and mobile apps, so the Google key only exists on the server (the apps keep only their platform-restricted map-rendering keys).

- `GET /places/autocomplete?input=&sessionToken=&latitude=&longitude=` → `[{ placeId, title, subtitle }]`
- `GET /places/:placeId?sessionToken=` → `{ label, latitude, longitude, viewport?: { southWest, northEast } }`

Rules worth keeping when touching it:

- `GOOGLE_MAPS_API_KEY` is **optional** in `env.ts` (so classmates without a key can still boot); `GooglePlacesClient` answers 503 when it is missing. It is sent only in the `X-Goog-Api-Key` header, never in a URL, and the key should be restricted in Google Cloud to Places API (New) + the server's IP.
- Every input is validated with `z.strictObject` before any Google call (unknown/repeated params rejected, `input` 3–200 chars without control chars, `sessionToken`/`placeId` limited to `[A-Za-z0-9_-]`, latitude/longitude parsed from strict decimal strings, both or neither). `validate(schema, "query" | "params")` replaces `req.query`/`req.params` with the parsed values via `Object.defineProperty`, since Express 5's `req.query` is a getter.
- Google's response is also validated with Zod. Google errors never reach the client: details 400/404 → 404, timeout (5s)/network/429 → 503, anything else → 502. Logs carry only Google's status code, never the key or the query text.
- Per-IP limiters on top of the global one: autocomplete 30/min, details 15/min. Responses are `Cache-Control: no-store` (Google's terms forbid caching Places content).
- **Daily quota (free-tier guard)**: Google Cloud can't cap this key, so the app does. Every Places call goes through `placesGateway` (`infra/places-gateway.ts`), a `PlacesQuotaGuard` around `GooglePlacesClient` — never instantiate `GooglePlacesClient` directly, or calls escape the count (collection-point address verification uses the same instance). Limits per SKU come from `PLACES_AUTOCOMPLETE_DAILY_LIMIT` / `PLACES_DETAILS_DAILY_LIMIT` (default 250 each → max 7,750/month, under the 10,000 free/month per SKU). The counter lives in MySQL (`PlacesApiUsage`, one row per SKU per São Paulo calendar day), so it survives restarts and holds across instances; a conditional `UPDATE ... WHERE count < limit` makes the check-and-increment atomic. The call is counted before reaching Google (failures count too). Over the limit → 503 without calling Google, until local midnight. `GET /places/usage` (ADMIN) shows today's used/limit/remaining.
- Fixed `languageCode: pt-BR`, `regionCode`/`includedRegionCodes: br`; results are biased to a 30 km circle around the client's coordinates, or around Manhuaçu when none are sent.

### Path alias

`tsconfig.json` defines `@/*` → `./src/*`, but **no runtime resolver (e.g. `tsconfig-paths`) is wired into `ts-node-dev` or the build**, so this alias only works for type-checking, not at runtime. Use relative imports in actual code; don't import via `@/...` until a resolver is added.

### Data model reference (from the docs' ER/class diagrams)

Most of the tables below already exist in `prisma/schema.prisma` (some still unused by any route, e.g. `Geolocation`, `Collection`, `DisposalRecord`, `Review`). The documented relational model (Portuguese names translated here to this project's English-identifier convention) is:

- **CollectionPoint** (`PONTO_COLETA`): id, collectorId (FK → User), name, city, latitude (decimal 10,8), longitude (decimal 11,8), whatsappContact, approvalStatus, credentialedAt, updatedAt, deletedAt (soft delete). Many-to-many with waste categories via a join table (`PONTO_CATEGORIA`).
- **OperatingHours** (`HORARIO_FUNCIONAMENTO`): id, collectionPointId (FK), weekday, openTime, closeTime.
- **WasteCategory** (`CATEGORIA_RESIDUO`): id, name, description, updatedAt, deletedAt.
- **DisposalRecord** (`REGISTRO_DESCARTE`): id, citizenId (FK → User), collectionPointId (FK), categoryId (FK), weightAmount (decimal), pointsEarned (int), disposedAt, updatedAt. This is what feeds gamification.
- **Review** (`AVALIACAO`): id, citizenId (FK), collectionPointId (FK), rating, comment, moderationStatus (enum), reviewedAt, updatedAt.
- **Achievement** / **UserAchievement** (`CONQUISTA` / `CONQUISTA_USUARIO`): badge/seal definitions (title, description, pointsRequired) and the join of which user earned which, when.
- **Notification** (`NOTIFICACAO`): id, title, message, sentAt, read.

The docs' class diagram also implies these role-specific behaviors (useful as a checklist of use-cases when scoping each module): Admin approves points, moderates content/reviews, manages users, publishes education content; Collector registers/updates their point and logs collected materials; Citizen browses/filters points, requests collection, logs disposals, rates points.
